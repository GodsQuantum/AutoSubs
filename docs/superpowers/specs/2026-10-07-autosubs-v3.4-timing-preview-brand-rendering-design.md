# AutoSubs v3.4 — Timing, Render-Faithful Preview, Presets, Brands and Fonts

**Date:** 2026-10-07
**Status:** Design approved in conversation; awaiting review of this written specification before implementation
**Repository:** `GodsQuantum/AutoSubs`
**Canonical workspace:** repository root
**Development runtime:** isolated DEV environment
**Production runtime:** remains untouched until explicit validation

## 1. Goal

AutoSubs v3.4 must make subtitle timing, line breaking, visual preview, preset application, brand routing, font selection and rendering behavior deterministic and trustworthy.

The central invariant is:

> A job has one resolved effective configuration. Transcription/word timing, segmentation, preview and final render must all consume that same effective configuration and the same canonical word timeline.

A second invariant is:

> What the user validates in the authoritative preview must match the final FFmpeg/libass render in typography, line breaks, positioning, colors, outlines, shadows and animation timing.

The release must remain a self-hosted Rust + Svelte application. No second application backend is introduced. Docker remains supported. AppImage packaging is a separate follow-up project, but v3.4 must preserve a single portable backend and the existing native folder-watcher architecture so AppImage can reuse it unchanged.

## 2. Current verified defects

### 2.1 Word timing

AutoSubs already requests `response_format=verbose_json` and `timestamp_granularities[]=word`. Speaches forwards this to faster-whisper with `word_timestamps=True`.

The current local model is `deepdml/faster-whisper-large-v3-turbo-ct2`. Its timestamps are native Whisper/faster-whisper word estimates, not a forced-alignment guarantee.

AutoSubs also contains paths that associate rendered visual tokens with `line.words` by positional index. Punctuation merging, French elisions/hyphen repair, user edits and normalization can change the display token sequence without necessarily changing the word timeline identically. This can make a visually displayed token inherit the wrong word timing even when the transcription endpoint returned useful timestamps.

### 2.2 Preset split-brain


prepare_job()` resolves the selected preset and uses `max_chars`, `max_lines`, format resolution and font size when creating subtitle groups.

However, a manually imported job is created with a default `job.format`, and `render_job()` later executes:

`preset.format = job.format.clone()`

Therefore the preset used during segmentation and the geometry used during rendering can diverge. The preset is also resolved again later instead of being frozen as the configuration that produced the subtitle layout.

This is the root architectural problem behind reports such as "the selected preset looks applied cosmetically but its cesure/format is not reliably the one rendered."

### 2.3 Preview drift

The current `FormatPreview.svelte` approximates libass with browser CSS (`font-size`, `-webkit-text-stroke`, `text-shadow`, estimated glyph width, etc.).

CSS browser layout and libass do not share font metrics, outline/shadow implementation, line-breaking or animation rendering. Exact parity is impossible with this as the authoritative preview.

### 2.4 Fonts

The current backend only scans the application `/fonts` directory. The browser then tries to reproduce the selected font using generated `@font-face` rules.

This does not expose the full server/system font catalog and still leaves browser rendering as a separate renderer from final libass output.

### 2.5 Brands

Today filename keywords live on `Preset`. `Brand` owns assets and defaults per format but has no filename routing keywords or visual override such as a brand highlight color.

That forces duplication of otherwise generic presets when only brand identity differs.

## 3. Architecture

### 3.1 `EffectivePreset`: one resolved configuration per job

Add a persisted, immutable-at-prepare-time `EffectivePreset` snapshot to each job.

It contains every property that can affect segmentation or rendering, including:

- format and fit mode;
- font family / face selection;
- size, bold, italic, uppercase;
- base, outline, highlight and shadow styling;
- X/Y placement;
- line spacing;
- animation style and animation parameters;
- `maxChars` and `maxLines`;
- outro selection after inheritance;
- brand-derived overrides;
- resolved render-related subtitle parameters.

The persisted snapshot is created before segmentation and becomes the only configuration consumed by:

1. segmentation;
2. editor preview;
3. regrouping;
4. ASS generation;
5. final render.

`render_job()` must not re-resolve the preset from current global state and must not overwrite one part of the resolved preset with an independent `job.format`.

A user action explicitly named **Apply preset** may replace the job snapshot. When it does, AutoSubs re-segments from the canonical stored word timeline using the new complete snapshot. It never silently applies only cosmetic fields.

Legacy jobs without a snapshot are migrated lazily by resolving their current preset once and persisting the result.

### 3.2 Configuration resolution precedence

Preset selection and brand selection are separate concepts.

#### Base preset precedence

1. Explicit preset selected during manual import or explicitly applied later.
2. Workflow preset when the job comes from a workflow.
3. Standalone preset filename-keyword match.
4. Brand default preset for the resolved output format.
5. Global/default preset.

An explicit preset selects the base layout/style and is never silently replaced by a filename match.

#### Brand resolution

A brand can be:

- selected explicitly by a workflow/job; or
- auto-resolved from `Brand.matchKeywords`.

Brand filename matching remains active even when a base preset was explicitly selected, because the brand is an overlay rather than a replacement preset.

When several brands match the same filename, choose the match containing the longest matching keyword. If there is still a tie, mark the resolution ambiguous and do *not* silently choose one; the UI exposes the ambiguity and asks for an explicit brand for that job/workflow.

#### Brand overlay

A brand may define:

- `matchKeywords`;
- optional `highlightColor`;
- existing logo/outro assets;
- default presets per format.

If a brand has a `highlightColor`, it overrides only the effective highlight color. It does not duplicate or mutate the underlying generic preset.

This enables:

- one generic 9:16 preset reused by several brands;
- each brand selected from filename keywords and applying its own highlight color;
- standalone presets with their own filename keywords and no brand;
- brand-specific presets when genuinely needed.

### 3.3 Canonical word timeline

Introduce a single canonical `TranscriptTimeline` contract whose words are stable semantic units rather than display tokens.

Each word stores:

- text;
- `start`;
- `end`;
- timing provenance;
- optional confidence.

Timing provenance is explicit:

- `forced-aligned`;
- `native-word`;
- `inferred`.

Display punctuation, French elision joining and hyphen joining must not destroy the mapping to the canonical timeline.

ASS animation generation must consume timeline-backed subtitle units, not reconstruct timing by `split_whitespace()` index.

Any fallback interpolation is allowed only when no usable word timing exists and must be marked `inferred`.

Text correction, including optional LLM correction, must preserve canonical timing identity. Corrections are reconciled against canonical units rather than replacing line strings positionally. Matched lexical units retain their original timing; merged units take the enclosing interval; genuinely inserted/unmatched units may receive inferred timing only and must be marked as such. A correction path must never silently convert an exact/forced-aligned timeline into positional whitespace timing.

### 3.4 Precision timing strategy

Keep transcription and alignment as two independent stages.

#### Stage A — transcription

AutoSubs continues using its OpenAI-compatible transcription provider. It may receive text and native word timestamps.

#### Stage B — alignment

Add an optional alignment provider interface. In **Precise** mode, AutoSubs aligns the accepted transcript against the original 16 kHz mono audio and replaces native/inferred word boundaries with forced-aligned boundaries when alignment passes validation.

The provider contract returns canonical words with start/end/confidence and does not perform subtitle line grouping. The transport is not part of the domain contract: an implementation may use an on-demand local process/library adapter or a configured HTTP provider. AutoSubs must not require a permanent alignment sidecar, and installations without an aligner remain functional with native timing.

For the target deployment, implementation must benchmark at least:

- current `deepdml/faster-whisper-large-v3-turbo-ct2` native timestamps;
- full `large-v3` native timestamps;
- forced alignment using a WhisperX-compatible CTC path with an explicitly permissive French alignment model such as `facebook/wav2vec2-large-xlsr-53-french` (Apache-2.0);
- stable-ts alignment/refinement as a comparison candidate.

The benchmark fixture must include the user's problematic French clip plus at least one clean speech fixture and one punctuation/elision-heavy fixture.

Create a small manually verified gold timing set for representative excerpts (waveform/spectrogram-assisted word boundaries). Report at minimum median absolute start-boundary error, median absolute end-boundary error, p95 boundary error, invalid/non-monotonic word count and real-time factor. A candidate may replace the current default only when it improves the timing-error distribution without introducing a material tail regression; runtime is then used as the secondary selection criterion.

The default selected production strategy is decided by measured timing error and runtime, not model reputation. The design preference is:

- `Precise` for word-sensitive animations (`word-by-word`, `karaoke`, `pop`, `highlight`, `bounce`);
- native timestamps may remain available as a faster mode;
- no non-commercial model may become a mandatory runtime dependency.

If forced alignment fails validation for a job, AutoSubs keeps the native word timeline, marks timing provenance accordingly, and surfaces the fallback in the UI instead of failing the entire job.

### 3.5 French segmentation / césure

Segmentation is a pure transformation:

`canonical timeline + EffectivePreset layout fields + output geometry -> SubtitleLine[]`

It must use the effective preset's:

- `maxChars`;
- `maxLines`;
- actual target output width;
- effective font size;
- font metrics proxy used by the existing layout algorithm.

Existing French protections remain mandatory:

- no orphaned apostrophe/elision;
- no split inside hyphenated compounds;
- keep short grammatical groups together where possible;
- preserve dialogue dashes;
- punctuation stays attached correctly;
- max-line and max-character constraints apply to manual imports, workflows, retranscription and explicit re-apply equally.

The job UI displays the resolved preset name, brand and the actual `maxChars × maxLines` used to create the current segmentation.

### 3.6 Render-faithful preview

The browser CSS preview is no longer authoritative.

Create a server-side preview renderer that shares the final render primitives:

- same `EffectivePreset`;
- same `generate_ass_content`;
- same format/fit/crop/scale geometry;
- same `fontsdir` / fontconfig;
- same libass;
- same subtitle event timing;
- same target resolution.

Refactor the FFmpeg visual filter construction so preview and final render call the same function rather than maintain duplicate filter graphs.

#### Preview behavior

For a job/editor:

- the user chooses/seeks a timestamp;
- the backend renders a still frame through the shared FFmpeg/libass visual chain;
- the UI displays that frame as the authoritative preview;
- style changes are debounced and request a new authoritative frame;
- while dragging X/Y controls, an optional lightweight CSS overlay may provide immediate motion feedback, but it is replaced by the server-rendered frame when the drag settles.

For preset editing without a source job, use a deterministic generated test canvas/video frame rendered through the same libass path.

The UI must visually distinguish a temporary live drag approximation from the settled authoritative render only if the approximation is shown for more than a trivial frame interval.

#### Parity verification

Regression tests must render the same fixture through preview and through the final visual pipeline and verify:

- same ASS content;
- same visual filter graph;
- same output geometry;
- same font resolution;
- same line breaks and subtitle positioning.

A visual regression fixture compares decoded frames with a strict perceptual threshold. Bit identity is not required after lossy video encoding, but subtitle geometry/style must be equivalent.

### 3.7 Fonts

Replace `/fonts`-only discovery with a `FontCatalog`.

Sources:

1. **System fonts** visible through fontconfig in the execution environment: the container catalog for Docker, and the desktop host catalog for the future AppImage.
2. **App fonts** stored in AutoSubs' configured fonts directory.

App fonts take precedence on family/name collision so a user can make a project reproducible. Preview and final render use the same generated fontconfig environment/order so this precedence is deterministic rather than dependent on browser or host lookup order.

The font catalog records:

- family;
- full name;
- style;
- weight;
- italic;
- source (`system` or `app`);
- canonical file path internally;
- stable public ID.

System font paths are never exposed as arbitrary browseable filesystem paths.

#### Custom font import

Add an explicit font import/upload action. Accepted font files are copied into the AutoSubs managed fonts directory. The stored filename is collision-safe and the catalog refreshes immediately.

The Docker installation keeps its `/fonts` persistent volume for app-managed fonts.

The future AppImage will use the same app-font directory under its application data location and merge it with desktop system fontconfig.

#### Rendering

Authoritative preview and final render resolve fonts via the same fontconfig/libass environment. Browser font availability is therefore irrelevant to visual correctness.

### 3.8 Subtitle shadow model

Replace the current single-size shadow approximation with explicit fields:

- `shadowOffsetX`;
- `shadowOffsetY`;
- `shadowBlur`;
- `shadowColor`;
- `shadowOpacity`.

Migration maps old `shadowThickness` to a compatible X/Y offset and preserves old color.

ASS rendering uses native libass/ASS tags where possible (`xshad`, `yshad`, blur and alpha/color) rather than custom image processing.

Preview uses the same ASS fields because it is server-rendered.

### 3.9 Numeric + slider controls

Create one reusable Svelte numeric-range control for continuous visual values.

Use both a slider and an editable numeric field for:

- font size;
- outline size;
- X/Y placement;
- shadow X/Y;
- shadow blur;
- shadow opacity;
- line spacing;
- floating/wobble speed where applicable.

Keep discrete values as selects/checkboxes and keep custom width/height as numeric fields only.

All controls support keyboard input, labels, min/max/step constraints and immediate validation.

### 3.10 Render profiles and time prediction

Add a per-render dropdown whose options come from runtime capabilities.

User-facing profiles:

- **Auto — recommandé**: selects the fastest validated stable encoder from runtime benchmarks and fallback order.
- **Rapide**: prefers the best validated hardware H.264 path.
- **Qualité**: selects the highest-quality validated H.264 policy for the runtime; it may resolve to software or hardware based on measured quality/stability rather than hard-coding libx264.
- **Compact** uses HEVC only when supported and explicitly selected; description warns about slower encoding and compatibility trade-offs.

The exact encoder selected is shown as secondary detail (for example Vulkan H.264, VA-API H.264, libx264).

Advanced users may still select a raw encoder/quality/preset in an advanced section, but the main UI uses profiles.

Each dropdown option has a one-line explanation and a time estimate.

#### Estimator

Use two data sources:

1. startup encoder benchmark already exposed by `h264BenchmarksMs`;
2. observed completed render history stored in SQLite, normalized by input duration, resolution/pixel count, encoder profile and whether an outro is appended.

Prediction is a range, not fake precision, e.g. `≈ 35–50 s`.

Until enough historical samples exist, use the startup benchmark as a coarse estimate and label it `estimation initiale`.

After successful renders, update the profile statistics using a bounded moving average. Failed encoder attempts do not pollute the successful throughput sample for the eventual encoder, but fallback frequency and observed fallback overhead are tracked separately and may widen the ETA range.

### 3.11 UI/UX pass

Apply the existing Superpowers workflow plus the current principles requested for the project:

- reduce duplicate controls and sources of truth;
- prefer native browser/Svelte controls over new UI dependencies;
- keep the main editor task-oriented;
- use progressive disclosure for advanced rendering/transcription settings;
- keyboard-accessible dialogs and controls;
- deterministic loading/error/empty states;
- no decorative animation that slows editing;
- preserve responsive/mobile behavior;
- no U+FFFD/source encoding regressions.

The editor should make the resolved state obvious:

- selected base preset;
- resolved brand;
- effective highlight override;
- timing quality/provenance;
- segmentation limits;
- selected render profile and ETA.

### 3.12 Similar-app features in scope

Features are accepted only when they improve subtitle editing rather than copy competitor surface area.

In scope:

- word-level timing display;
- fine timing nudge for a selected word/unit;
- explicit line-break editing;
- re-group from canonical word timing;
- per-word text correction without destroying timing;
- saved reusable visual presets;
- safe-zone preview;
- clear timing provenance.

Out of scope for v3.4:

- generative B-roll;
- auto emojis/stickers;
- clip generation;
- social publishing;
- speaker diarization unless needed by a later request.

## 4. Data model changes

### Job

Add persisted fields conceptually equivalent to:

- `effectivePreset: EffectivePreset | null`;
- `resolvedBrandId?: string`;
- `timingQuality`;
- `renderProfile` / render override;
- render estimate metadata when relevant.

Keep `presetId` as a provenance/reference, not as the live source of rendering truth.

### Preset

Retains standalone `matchKeywords`.

Add new shadow fields and migrate legacy `shadowThickness`.

No preset must require a brand.

### Brand

Add:

- `matchKeywords?: string`;
- `highlightColor?: string`.

Existing assets/default-preset mapping remains.

### TranscriptTimeline

Extend timing provenance and optional confidence while preserving backward-compatible migration of old stored timelines.

## 5. API changes

Add/extend endpoints for:

- authoritative render preview frame;
- font catalog listing;
- font import/upload;
- render profiles/capabilities including explanation and ETA;
- explicit apply-preset-to-job action that re-segments from canonical timeline;
- optional word timing nudge/edit;
- current effective job configuration.

Existing API contracts remain backward compatible where feasible. New fields use serde defaults so old persisted JSON/SQLite records migrate safely.

## 6. Failure handling

- Alignment unavailable: keep native timestamps, mark fallback.
- Alignment returns non-monotonic/invalid timestamps: reject aligned result and keep prior valid timeline.
- Font disappears between preset save and render: job reports the missing face and does not silently substitute another font for authoritative preview/final render.
- Preview render fails: display the backend error; do not silently fall back to CSS and call it accurate.
- Multiple brand keyword matches with equal specificity: surface ambiguity; no arbitrary brand. A manual job requires explicit resolution before final render. An unattended workflow fails preparation with an actionable ambiguity error and leaves the source unarchived, preserving the current retry/failure safety contract.
- Render profile's preferred encoder fails: existing validated fallback chain may continue, and the actual encoder used is recorded.
- Preset deleted after a job is prepared: the persisted effective snapshot keeps the job renderable.
- Preset edited after a job is prepared: existing job does not silently change; user explicitly reapplies it to update/regroup.

## 7. Testing requirements

### Rust unit/integration

Add regression tests covering:

- manual import with explicit preset applies format, `maxChars`, `maxLines`, typography and animation from one snapshot;
- workflow and manual import produce equivalent segmentation for equivalent effective configuration;
- render never re-resolves a prepared job's preset;
- changing/deleting a global preset after prepare does not mutate prepared jobs;
- applying a new preset explicitly re-segments from canonical timing;
- brand keyword overlay modifies highlight without cloning/replacing the generic base preset;
- ambiguous brand matches are surfaced;
- standalone preset keyword routing still works without brands;
- token normalization preserves canonical word/timing identity;
- ASS word animations consume canonical timings and not whitespace-index fallbacks when exact timing exists;
- shadow migration and ASS tags;
- system/app font precedence and safe font lookup;
- render estimate history ignores failures.

### Preview parity

Add a fixture test that:

1. builds a known effective preset;
2. creates its ASS;
3. renders an authoritative preview frame;
4. renders the equivalent final visual pipeline;
5. asserts shared graph/config plus strict visual equivalence.

Fixtures include a custom app font and a system font.

### Frontend

Add tests for:

- slider + numeric synchronization;
- effective preset/brand/timing badges;
- render profile descriptions and ETA states;
- font source labels;
- preview loading/error/latest-wins behavior;
- preset application action;
- accessibility and encoding guards.

### End-to-end isolated DEV validation

Before user validation:

- use a copy/non-destructive input from the problematic recent French job;
- compare old/native timing versus selected precise strategy;
- verify word-by-word visually;
- verify cesure with the actual preset;
- verify font parity;

No production changes occur during this validation.

## 8. Implementation decomposition

This umbrella design is implemented as sequential, independently verifiable plans rather than one monolithic patch:

1. **Core correctness** — effective preset snapshot, brand/preset resolution, canonical word identity, segmentation and correction mapping.
2. **Precision timing** — benchmark harness, gold timing fixtures, alignment provider and timing provenance/fallback.
3. **Render fidelity** — shared preview/final visual graph, font catalog/import, shadows and numeric-range controls.
4. **Render UX + hardening** — render profiles/ETA, editor state visibility, similar-app editing improvements and final accessibility/performance pass.
5. **DEV deployment validation** - isolated runtime, smoke/E2E comparison, temporary route switch only after health checks, then user validation.

Each plan must leave the branch green and preserve the interfaces produced by earlier plans. The AppImage remains a separate follow-up specification.

## 9. Development and deployment isolation

Development happens only in the isolated DEV runtime.

The existing production AutoSubs service retains its data/config.

The isolated DEV runtime gets:

- independent application process/container;
- independent config/data/SQLite state;
- access only to the required source/media paths using existing mount architecture;
- no production database reuse.

Once the DEV build passes health and smoke tests, the existing AutoSubs reverse-proxy route may temporarily point to DEV for user validation. Production remains intact so rollback is only a route change.

No GitHub push, release or production image update occurs before explicit user validation.

After validation:

1. complete full test/format/lint/build suite;
2. code review;
3. push branch / PR;
4. merge only after required CI is green;
5. publish official GHCR image through the existing release/image workflow;
6. update production from the official upstream image;
7. smoke-test production;
8. restore the route to production;
9. remove temporary DEV routing and build artifacts.

## 10. Performance constraints

- Preview requests are cancellable/latest-wins.
- Debounce style changes so dragging does not spawn an unbounded FFmpeg queue.
- Preview rendering has a small bounded worker pool independent from full renders.
- Transcription/alignment concurrency remains bounded separately.
- No new permanent sidecar daemon is introduced when a library/process call inside an existing owned service suffices.
- Keep idle memory/CPU low.
- Do not monopolize the transcription service while AutoSubs frontend/backend builds run; compilation remains in the isolated DEV runtime.

## 11. Security and filesystem constraints

- Do not change established deployment mounts.
- Preserve user `arezki` write/control semantics on project and production paths.
- App font import writes only to the configured app-font root.
- System font discovery is read-only.
- All existing allowed-root protections remain.
- Preview/temp files live under AutoSubs work/config data and are cleaned after use.
- No secret/API key is committed to Git.

## 12. AppImage follow-up boundary

The AppImage is intentionally a second spec after v3.4 behavior is validated.

v3.4 must make that future packaging straightforward by preserving:

- one Rust backend;
- one Svelte frontend;
- the existing native `notify` folder watcher + reconciliation scan;
- configurable data/config/fonts directories;
- no Docker-only business logic.

The future AppImage will package this same application, add desktop integration and choose appropriate XDG paths. It will not fork a separate watcher/backend implementation.

## 13. Acceptance criteria

v3.4 is ready for user validation only when:

1. the problematic word-timing case is measurably improved and timing provenance is visible;
2. selected preset segmentation fields are demonstrably applied to manual imports;
3. preview and final render use the same ASS, font resolution and visual FFmpeg/libass path;
4. preview line breaks, font, position, outline, highlight and shadow match final rendering;
5. system fonts and app-imported custom fonts can both be selected and render identically in preview/final;
6. brands can route by filename keyword and override highlight color over generic presets;
7. standalone preset keyword routing still works;
8. shadow offset/color/blur/opacity controls work;
9. relevant continuous controls expose both slider and numeric values;
10. render profiles show concise explanations and a defensible time range;
11. isolated DEV tests/build/smokes are green;
12. production has not been modified before explicit user approval.
